## 25-1 Production request path

常見架構：

```text
Internet
  ↓ HTTPS
Reverse proxy / load balancer
  ↓
WSGI/ASGI server
  ↓
Django
```

每一層都有不同責任。

---

<!-- source: D4:003 | 03_deployment_and_operations/04_process_proxy_logging.md | line 30 -->

## 25-2 Reverse proxy 常做什麼？

- TLS termination
- domain / virtual host
- static file serving
- request size / timeout
- rate limit
- compression
- access log

Django 不需要自己做完所有網路層工作。

---

<!-- source: D4:004 | 03_deployment_and_operations/04_process_proxy_logging.md | line 44 -->

## 25-3 WSGI / ASGI server

Django 提供：

- `config/wsgi.py`
- `config/asgi.py`

Production 常交給 Gunicorn、uWSGI、Uvicorn/Daphne 或平台內建 server。

選擇取決於 sync/async、平台與運維方式，不是「哪個名字最潮」。

---

<!-- source: D4:005 | 03_deployment_and_operations/04_process_proxy_logging.md | line 57 -->

## 25-4 Process manager 要解決什麼？

- crash 後重啟
- 多 worker
- graceful shutdown
- boot on restart
- stdout/stderr 收集
- health check

systemd、container orchestrator、PaaS 都可以扮演這個角色。

---

<!-- source: D4:006 | 03_deployment_and_operations/04_process_proxy_logging.md | line 70 -->

## 25-5 Log 不只 `print()`

至少分：

- application log
- access log
- error log
- audit/security log（視需求）

Production log 應可搜尋、保留適當期間，且不要洩漏 secrets/password/token。

---

<!-- source: D4:007 | 03_deployment_and_operations/04_process_proxy_logging.md | line 83 -->

## 25-6 Django logging 心智模型

```python
import logging
logger = logging.getLogger(__name__)

logger.info("article published", extra={...})
```

真正 production 可以把 handler 指到 stdout，再由平台集中收集。

---

<!-- source: D4:008 | 03_deployment_and_operations/04_process_proxy_logging.md | line 96 -->

## 25-7 可觀測性

至少知道三種訊號：

- logs：發生了什麼
- metrics：整體趨勢
- traces：一次 request 穿過哪些服務

本課先把 log、HTTP status、response time 建立起來，再延伸監控。

---

<!-- source: D4:009 | 03_deployment_and_operations/04_process_proxy_logging.md | line 108 -->

## 25-8 Health check

Health endpoint 不等於「首頁回 200」。

要思考：

- process alive
- app ready
- database 是否必要
- 外部 service 掛掉時是否也要判 unhealthy

過度嚴格的 health check 也可能造成重啟風暴。

## 26-1 先備回顧：資料模型與檔案

[資料層教材](04_Model與欄位設計.md#chapter-6) 已建立本章需要的觀念：

- Model 描述資料；migration 記錄結構的變更。
- unique／constraint 加入前，既有資料也必須符合規則。
- ImageField 保存 storage 路徑參照；DB 備份不包含圖片內容。
- Admin 改資料與修改 schema 不同；後台操作也需權限與紀錄。

本章接著處理正式部署順序、備份及復原。

---

<!-- source: D5:003 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 25 -->

## 26-2 Migration 是版本化 schema 變更

部署前先確認：

```bash
uv run python manage.py makemigrations --check
uv run python manage.py showmigrations
```

不要在 production 現場才臨時產生 migration。

---

<!-- source: D5:004 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 38 -->

## 26-3 Deploy 順序要能相容

理想的 migration：

1. 新舊 code 短時間可以共存
2. 先新增 nullable/default 欄位
3. backfill data
4. code 切換讀新欄位
5. 最後再移除舊欄位

這是 expand → migrate → contract 思路。

---

<!-- source: D5:005 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 52 -->

## 26-4 Data migration 也會失敗

LearnJournal 03A 已有 `RunPython`。

Production 額外要想：

- 資料量多大？
- transaction 多久？
- 會鎖表嗎？
- 可以重跑嗎？
- rollback 真的可逆嗎？

---

<!-- source: D5:006 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 66 -->

## 26-5 Backup 的最低標準

你要能回答：

- 備份什麼？DB / media / config
- 多久一次？
- 保留多久？
- 放在哪裡？
- 誰能讀？
- 有沒有測過 restore？

「有 backup job」不等於「能恢復」。

---

<!-- source: D5:007 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 81 -->

## 26-6 RPO / RTO

兩個常用概念：

- RPO：最多能接受遺失多少時間的資料？
- RTO：服務最多能停多久？

這兩個答案決定 backup 頻率與 recovery 設計。

---

<!-- source: D5:008 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 92 -->

## 26-7 Rollback 不只是 git revert

Code rollback 容易；database rollback 可能困難。

例如：

- 新 code 已寫入新 schema
- migration 已刪欄位
- data migration 不可逆

所以 schema change 要設計向前/向後相容窗口。

---

<!-- source: D5:009 | 03_deployment_and_operations/05_migrations_backup_recovery.md | line 106 -->

## 26-8 Classroom recovery drill

SQLite 可以做最小演練：

```bash
cp db.sqlite3 db.sqlite3.backup
# 做一個破壞性操作
cp db.sqlite3.backup db.sqlite3
```

這只是概念演練；production PostgreSQL 應使用原生/managed backup 與 restore 流程。

## 27-1 最小 CI gate

每個 Django 專案至少：

```bash
uv run python manage.py check
uv run python manage.py makemigrations --check
uv run python manage.py test
```

Repository 教材再加：

```bash
python scripts/check_material_links.py
```

---

<!-- source: D6:003 | 03_deployment_and_operations/06_ci_and_release_checklist.md | line 30 -->

## 27-2 為什麼 `makemigrations --check`？

它抓這種情況：

```text
models.py 已改
migration 忘了 commit
```

沒有它，production migrate 可能「成功」但 schema 根本沒包含你的 model change。

---

<!-- source: D6:004 | 03_deployment_and_operations/06_ci_and_release_checklist.md | line 43 -->

## 27-3 CI 不應保存 production secrets

Test settings 使用：

- SQLite / disposable DB
- locmem email/cache
- fake credentials

若 integration test 必須用 secret，使用 CI secret store，不要寫進 YAML。

---

<!-- source: D6:005 | 03_deployment_and_operations/06_ci_and_release_checklist.md | line 55 -->

## 27-4 Release 前 checklist

- tests green
- migrations reviewed
- backup verified
- environment variables present
- `DEBUG=False`
- `ALLOWED_HOSTS` correct
- static collected
- health check ready
- rollback plan understood

Checklist 不是官僚文件，是把記憶外部化。

---

<!-- source: D6:006 | 03_deployment_and_operations/06_ci_and_release_checklist.md | line 71 -->

## 27-5 Release 後驗證

Smoke test：

- homepage 200
- login/logout
- 一個核心 CRUD flow
- static/media 可讀
- DB write 正常
- error log 沒爆量
- scheduled job 有在跑

---

<!-- source: D6:007 | 03_deployment_and_operations/06_ci_and_release_checklist.md | line 85 -->

## 27-6 監看 deployment

上線後短時間重點看：

- 5xx rate
- latency
- database errors
- login failures
- background job failures
- disk/storage usage

不要部署完就關 terminal 當作完成。

---

<!-- source: D6:008 | 03_deployment_and_operations/06_ci_and_release_checklist.md | line 100 -->

## 27-7 Roll forward vs rollback

小錯誤有時候最快是 hotfix roll forward；重大或未知風險才 rollback。

重點是事先知道：

- code 是否可 rollback
- migration 是否相容
- data 是否被不可逆修改

```text
Code + tests
   ↓
Environment / secrets
   ↓
Database + migrations
   ↓

   ↓
WSGI/ASGI + proxy + HTTPS
   ↓

   ↓

```
